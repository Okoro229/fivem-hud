Optimiser les scripts serveur FiveM : Guide technique 2026 (≈ 600 mots)

1. Pourquoi l’optimisation côté serveur ?

FiveM exécute du Lua (et parfois du C#) sur le serveur pour gérer la logique de jeu, les bases de données et les interactions entre joueurs. Un script mal écrit peut monopoliser le thread principal, augmenter le tick‑rate et provoquer des baisses de FPS, du lag ou même des plantages. Les guides publiés en 2025‑2026 (FiveVault, RARXNetwork, Frozen‑Scripts et Pityus) s’accordent sur cinq leviers majeurs : nettoyage des ressources, amélioration des accès DB, bonnes pratiques de script, redémarrages planifiés et réglages hardware.

2. Profilage de base – resmon et les logs

  • resmon (Four​ned‑Scripts, 2025) permet de visualiser le temps CPU consommé par chaque ressource.
  • Identifiez les scripts dont le “CPU usage” dépasse 5 % du tick moyen ; ce sont les premiers candidats à l’optimisation.

Exemple d’extraction de données :


RegisterServerEvent('monitor:cpu')
AddEventHandler('monitor:cpu', function(resource, ms)
    if ms > 5.0 then
        print(('Resource %s uses %.2f ms per tick'):format(resource, ms))
    end
end)

3. Réduire les boucles lourdes

3.1. Éviter les boucles imbriquées sur de grands tableaux

Beaucoup de lag provient de for i = 1, #players do for j = 1, #players do … end end qui s’exécute chaque tick. La solution : pré‑filtrer, limiter la portée ou remplacer par des tables de lookup.


-- Mauvais : boucle O(n²) chaque tick
for _, p1 in ipairs(players) do
    for _, p2 in ipairs(players) do
        if p1 ~= p2 and #(p1.pos - p2.pos) < 10.0 then
            TriggerClientEvent('showProximity', p1.id, p2.id)
        end
    end
end

-- Optimisé : table de proximité mise à jour toutes les 2 s
local proximityMap = {}

CreateThread(function()
    while true do
        proximityMap = {}
        for i = 1, #players do
            local p1 = players[i]
            proximityMap[p1.id] = {}
            for j = i+1, #players do
                local p2 = players[j]
                if #(p1.pos - p2.pos) < 10.0 then
                    table.insert(proximityMap[p1.id], p2.id)
                    table.insert(proximityMap[p2.id], p1.id)
                end
            end
        end
        Wait(2000)   -- 2 s au lieu de chaque tick
    end
end)

-- Tick léger : uniquement lecture du cache
CreateThread(function()
    while true do
        for id, neighbours in pairs(proximityMap) do
            TriggerClientEvent('showProximity', id, neighbours)
        end
        Wait(0)   -- run‑once per tick
    end
end)

3.2. Utiliser Wait (sleep) lorsque le script n’a rien à faire

Le guide de Pityus (sep 2026) recommande “sleep long when nothing is happening”. Un script qui attend un événement doit appeler Wait(5000) au lieu de rester actif.


CreateThread(function()
    while true do
        local data = MySQL.Sync.fetchAll('SELECT * FROM vehicles WHERE parked = 0')
        if #data == 0 then
            Wait(30000)   -- 30 s d’inactivité
        else
            ProcessVehicles(data)
            Wait(1000)    -- 1 s entre chaque lot
        end
    end
end)

4. Caching des valeurs fréquentes

4.1. Cache des fonctions natives

Les appels à GetEntityCoords ou GetPlayerName sont coûteux lorsqu’ils sont répétés dans une même boucle. Stockez le résultat dans une variable locale.


local coords = GetEntityCoords(playerPed)   -- cache local
if #(coords - somePoint) < 5.0 then
    -- …
end
